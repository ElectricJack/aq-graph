## Source-backed core requirements

Before this compatibility increment, the aq-graph baseline had workspace capabilities and immutable history, but let every workspace writer edit every knowledge node, accepted arbitrary provenance objects, permitted direct verification badges, preserved verification after content edits, and returned retired/disputed knowledge in default search. The translated assertions first demonstrated those gaps, then verified the corrected behavior.

The graph contract exercised by these translations is:

- `created_by` records the authenticated creator and is immutable. A `write` principal can read workspace knowledge and edit its own unverified findings. An `admin` can correct another author's finding. Protected verified or disputed knowledge requires admin edits. AQ session, task claim, and supervisor identities are mapped to these credentials by an external adapter.
- Ordinary creation produces unverified knowledge. Ordinary patches cannot set `verification` to verified/disputed. `verify_knowledge` takes an expected version, verified/disputed assertion, named evidence, and nonempty mutation reason. Admin performs the assertion, and the server records `last_verified_by` and `last_verified_at`. This is an attributed assertion, not proof that the claim is true.
- A meaningful protected content edit invalidates verification and clears current verification actor/time, while retaining evidence descriptors and old immutable snapshots. A no-op edit does not invalidate it or create a revision.
- Provenance descriptors have nonempty unique `source_id`, a supported typed `kind`, correctly typed required fields, and matching field sets. The translation tests portable URL descriptors and Git object IDs. AQ task/review/artifact descriptors require a separate authorized source adapter; unsupported kinds must fail explicitly.
- Retirement requires admin and a nonempty reason, retains history and identity, and differs from deletion. Reasons contain at most 4096 bytes and belong only to retired state. Ordinary edits and outgoing link changes to retired knowledge fail until restoration. Restore uses the same logical revision engine as tasks. It restores exact content and recorded relationship membership as a new revision, preserving current retirement state/reason and tombstone by default. Explicit `include_lifecycle` restores the historical lifecycle. Meaningful restoration clears verification under current policy in either mode; a true no-op preserves the current assertion, and a historical badge is never revived.
- Search excludes retired and disputed knowledge by default and supports explicit `include_retired=true` / `include_disputed=true`. Direct authorized reads and history still retain those records.
- A writer may submit an immutable named draft correcting another author's finding, while only admin applies knowledge proposals. Application rechecks expected versions and authority, commits once, and is idempotent.
- Credential downgrades and revocation are rechecked before an idempotency receipt is replayed; a receipt is not an authorization bypass.

The JSON mutation is `{"op":"verify_knowledge","id":"UUID","expected_version":1,"verification":"verified","evidence":[...]}` inside the existing mutation envelope. Retirement uses `update_node` with `patch.retired=true`, `patch.retirement_reason`, and the envelope's reason. Names and exact status categories should stay synchronized with `docs/api.md` and the published schema when implemented.

## Unified revision semantics superseding the first adaptation

The later shared version-control contract applies to tasks and knowledge identically: `content_revision` now advances for every durable planning, lifecycle, deletion and owned relationship change. It is retained as a compatibility field name rather than a content-only counter. Exact revision reads return both the node and immutable owned edge versions. Owned relationships include all outgoing edges plus incoming execution dependencies and parent membership; other incoming informational edges remain derived.

This intentionally changes the initial aq-graph adaptation that kept unverified link edits separate from the source revision and restored knowledge lifecycle implicitly. The v1 retirement/restore test now opts into historical lifecycle restoration explicitly with `include_lifecycle:true`; default restore preserves current task state, retirement/reason and deletion. Knowledge verification policy still prevents restoring an old badge as current trust. Historical link sets are never reconstructed from current state: legacy revisions without retained membership report unavailability and cannot be restored safely.

`tests/unified_versions.rs` tests these shared semantics for both kinds, including stable edge IDs and monotonic edge versions, source pins/descriptions, parent/prerequisite membership, stale CAS and concurrent idempotent restores, lifecycle flags, exact immutable history, scope, and rollback when historical relationships violate the current graph. Whole-graph historical reconstruction and v1's exact UUID/hash wire format remain outside this contract. A bounded atomic batch can produce per-operation record revisions; a v1 proposal's single combined-revision shape is not claimed solely from batch atomicity.

## Common revision update

`revision ID --revision N` exposes the exact logical node plus its recorded relationships for either kind; diffs include relationship changes. Each meaningful lifecycle/content/membership mutation advances that record’s CAS version and `content_revision`. Outgoing informational changes therefore participate in source knowledge history, while incoming informational references remain owned by their source. Incoming structural edges are included in task snapshots. Full target content is not recursively frozen: floating/pinned target semantics remain explicit.

Migration 0006 preserves old snapshots and appends an attributed complete baseline. Old snapshots without relationship sets return `relationships_available:false` with `links:null`; restore rejects that unknown historical relationship state. Shared restore does not bypass author/admin ownership, source access, graph invariants or verification reset. The source inventory keeps schema-5 evidence separately and records current passing focused schema-6 tests for the common version-control contract; partial v1 cases remain open.
