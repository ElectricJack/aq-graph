# Schema 7 aborted optimized-query experiment

**This run was aborted after a severe early regression and is not a completed acceptance run.** The retained fixed-concurrency stages completed before termination; open-loop traffic was interrupted and has no complete client phase report. Partial request logs and telemetry are retained, with the abort timestamp/reason in `aborted.json`. These results do not establish burst recovery or the 200/s target.

First-touch traffic completed only 22.9 attempts/s with p95 4519 ms and ten HTTP 503 responses. Warmup remained at 22.8/s with p95 5056 ms and 118 HTTP 503 responses. The 50-client stage completed 29.1/s with 180 HTTP 503 responses; ready p95 was 6032 ms, search 5374 ms and history 2767 ms. All HTTP 503 envelopes reported `overloaded`. The later 100-client stage completed 226.5/s with 112 HTTP 503 responses, and 200 clients completed 266.9/s without HTTP 503, but this transient improvement does not establish a full successful profile.

Post-abort statistics show automatic vacuum completing for history at 17:32:51 UTC, nodes at 17:33:08, link sets at 17:33:08, memberships at 17:33:12 and edge versions at 17:33:17, overlapping the early overloaded stages and their subsequent improvement. The nodes table then had 33,113 of 33,177 pages marked all-visible. Exact post-abort prepared plans use index-only scans and measure readiness at 95/64 ms custom/generic; history is 0.55–0.72 ms in both modes. The timing and visibility-sensitive access paths are consistent with a maintenance/visibility effect, but pre-run visibility was not captured and causality is unproven. This experiment exposes sensitivity that the isolated post-baseline plans did not establish. A separately labeled explicit-VACUUM steady-state followup will retain the resulting mutated graph state and record new growth snapshots; it is not a normalized percentage comparison with the original baseline.

This rerun follows the [retained baseline](../schema7-load/README.md) on the same shared desktop hardware, release profile, loopback endpoints, PostgreSQL 17 container, pool size 20 and durability settings. The benchmark database was dropped and recreated, then seeded with the same deterministic 100,000-node/500,000-edge fixture; the baseline's mutated state is not reused. All baseline artifacts remain intact.

The runtime changes are readiness candidate selection before full node fetch, materialized node history matching before sequence pagination, and `SET jit=off` on each application pool connection. They preserve the API's ready/history semantics. Read-only full-JSON ready candidate parity passed nine representative cursor/limit cases before integration; the parent independently ran the full PostgreSQL-backed test suite and deployment recovery drill before the measured run. PostgreSQL's default `jit` remains on for administrative sessions; the service pool explicitly turns it off. Query plans here explicitly use the service setting.

The sole workload harness timing change records the shared phase clock in the barrier action before releasing fixed-concurrency workers. This removes a small epoch-boundary race in baseline service-log grouping and gives workers a common deadline. The baseline's exact measured harness is retained in its directory. Seed metadata additionally records PostgreSQL default JIT settings. Workload selection, durations, concurrency, arrivals and queue bounds are unchanged.

All baseline measurement limitations apply: warm OS/database caches, local HTTP without TLS/Cloudflare, shared desktop rather than an agreed reference VPS, sampled resource/wait telemetry rather than direct pool wait durations, no controlled maintenance or large long-term storage-growth scenario, and no agreed service p99 budget. The 200 open-loop workers remain below the service admission limit of 256. Expected conflict/validation responses count as errors; bounded client queue drops remain failed offers. Open-loop `client_queue` is residual total-minus-HTTP delay, including small client processing overhead. Fixed service logs group by completion time; non-overlapping open-loop arrival windows can contain previous-phase tails.

The same owner-only secret inputs remain in ignored `.local/schema7-load-optimized` files. Container `aq-graph-schema7-load-pg`, named volume `aq-graph-schema7-load-data`, database `aq_graph_bench_schema7`, PostgreSQL port 55434 and service port 18745 are isolated from AQ v1. A distinct parent validation database was preserved when recreating the fixture. Exact workload/seed arguments, source/binary hashes, collection scripts, raw results/logs and before/after counts accompany this report.
