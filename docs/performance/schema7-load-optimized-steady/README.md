# Schema 7 post-maintenance steady-state workload

**Overall performance acceptance remains unmet. The maintained steady-state run completes all 6,000 initial 200/s offers without drops, but it still misses ready/search latency targets and does not absorb the 1,000/s burst.** This is operational evidence for the declared warm condition, not a production-readiness or controlled baseline speedup claim.

Completed attempts per completion window are 198.50/s, 276.57/s and 199.28/s. Tails are 0.227, 1.484 and 0.104 seconds; phase completion windows overlap and must not be added. There are no HTTP 503, transport errors or socket timeouts anywhere in this full profile. HTTP 400 envelopes are expected dependency validation rejects; HTTP 409 envelopes are hot-record version conflicts. They remain errors rather than being excluded from latency or success denominators. Recovery has one failed client offer and elevated early latency, so recovery is not perfect. The last ten-second service-completion window contains 1999 completions with overall p95 221 ms, compared with 2389 completions/p95 778 ms in its first ten seconds (which includes burst tails).

At initial 200/s sustained arrivals, per-operation client p95 is get 3.9 ms, context 9.7 ms, independent history-preserving update 19.7 ms, ready 164.8 ms and search 305.2 ms. Service-completion-window p95 is get 2.7 ms, context 8.0 ms, all mutation subtypes 17.0 ms, ready 163.7 ms and search 304.5 ms. Thus get/context/small-update observations fit provisional budgets in this warm condition, while ready exceeds 100 ms and common-term search exceeds 200 ms. Mutation route timing includes retries and duplicate dependency calls; independent-update client timing is the separate fresh-write measure. Service groups are completion-window aggregates, not exact request-origin client groups. No agreed service p99 budget exists.

Fixed-client stages drive the service close to saturation and still miss provisional operation latency targets. At 50 clients, service p95 is get 184.7 ms (budget 25), context 184.6 ms (100), mutations 194.5 ms (100), ready 350.6 ms (100), and search 548.2 ms (200): each measured operation budget is missed. Their measurements are retained without treating the favorable 200/s arrival test as a substitute.

Post-run forced custom/generic exact plans (with service `jit=off`) take 89/74 ms for readiness and 0.64–0.89 ms for history across low/middle/high revision-rich nodes. Common search takes 95/146 ms, while selective/missing terms take about 0.9–1.8 ms. Forced plans remain isolated diagnostics and do not identify the actual cached plan chosen on each service connection during traffic.

The actual starting graph contains 100,000 nodes, 500,001 edges, 301,873 revisions and 801,874 history entries, including 1873 revisions/1874 history entries from the interrupted experiment. This run adds 4528 revisions and 4528 history entries, zero edges/edge versions, and 5366 change sets. Duplicate successful dependency requests do not establish edge-ingestion throughput. Database allocation increases 38,395,904 bytes (36.6 MiB), with approximately 9.9 MiB receipts, 9.4 MiB revisions, 9.3 MiB history and 8.0 MiB change-set growth. Allocation includes indexes/TOAST/free space, not only logical content.

PostgreSQL peaks at 1779% CPU (17.8 logical cores); service and generator peaks are 64% and 73% of one core. Observed peak RSS is 56.8 MiB for service and 139.9 MiB for generator; PostgreSQL container samples range about 2.72–2.80 GiB. Wait-event and cumulative I/O/database samples remain in the raw telemetry. This is a single sequential experiment on shared hardware; it does not isolate query, JIT, cache or maintenance effects statistically.

This is a distinct steady-state followup to the [aborted optimized experiment](../schema7-load-optimized/README.md). It reuses that experiment's mutated graph and running optimized service (including warm prepared-statement caches), after explicit all-table `VACUUM (ANALYZE, VERBOSE)` completed in 3.89 seconds. No reseed occurs. New before/after snapshots measure this run's growth separately; the inherited seed manifest describes the initial underlying fixture, while `database-before.json` describes the actual starting graph. The initial phase named `first_touch` is followup traffic after maintenance, not a cold-cache or new-service measurement.

Before this run, no active vacuum or query remained; twenty service connections were idle. Every public relation was fully all-visible except nodes (33,008/33,177 pages, 99.49%). Default VACUUM bypassed index cleanup on 169 node pages with 1809 dead item identifiers; its log reported zero not-yet-removable tuples. These explicit conditions matter: the preceding fresh-seed experiment suffered seconds of latency and HTTP 503 responses while automatic vacuum overlapped the workload. The temporal association and visibility-sensitive query plans support investigation but do not prove a single cause.

Runtime, workload and hardware remain those of the optimized experiment: Rust release build, pool 20, service port 18745 and PostgreSQL port 55434 on loopback, 100k initial nodes/500k initial edges, durable PostgreSQL 17.11, 50/100/200 fixed clients and 200/1000/200 arrivals per second. The service explicitly sets `jit=off` per pool connection; PostgreSQL's default administrative setting remains on. The deterministic workload runs five seconds of initial traffic, ten seconds warmup, thirty seconds per concurrency, and open-loop thirty/ten/thirty seconds, plus setup and tail completion. The host is an unpinned shared WSL2 desktop (Ryzen 9 5900X, 24 logical CPUs, approximately 31.3 GiB RAM), not an agreed reference VPS.

This followup's warm/maintained and previously mutated state differs from the original baseline. It cannot support a controlled percentage speedup claim or isolate the effect of the combined query/JIT changes. Expected conflict/validation failures remain errors; queue drops remain failed offers. Socket timeout is per blocking I/O, distinct from the ten-second service deadline. Client latency, residual client delay, service guard timing and PostgreSQL/process resource telemetry retain their separate meanings. Service logs here are filtered from this run's start; the prior aborted logs remain in their original directory.

Pool wait durations, controlled cold caches, maintenance under a deliberately timed production-like schedule, long-term history growth, TLS/Cloudflare, production admission rejection above 256 requests, and an agreed service p99 budget remain gaps. PostgreSQL wait snapshots do not measure pool waits. The 200 open-loop workers remain below the admission limit, so burst shedding can happen in the bounded client queue. `maintenance.json` and `maintenance.log` retain the precondition operation; exact measured harness, arguments, source/binary hashes and collection scripts accompany the workload results.
